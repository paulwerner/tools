# Arty — Game Asset Processing Toolkit

## Product Requirements Document

**Version:** 1.0
**Status:** Draft

---

## 1. Overview

Arty is a client-side game asset processing toolkit built with Svelte and TypeScript. It provides a non-destructive, operation-stack-based workflow for common game asset tasks — primarily sprite sheet assembly from individual frames, but extensible to scaling, palette manipulation, background removal, and future 3D asset support.

The tool targets indie game developers and hobbyists who need a lightweight, browser-based alternative to heavyweight tools like TexturePacker or Aseprite's export pipeline. It runs entirely in the browser with no server dependency, making it suitable for local personal use now and web deployment later.

### 1.1 Design Principles

- **Non-destructive editing.** Every operation is reversible. The original source images are never modified. An operation stack tracks all transformations, and any operation can be toggled, reordered, or removed with live preview updating accordingly.
- **Extension-first architecture.** The initial workflow is linear (load → configure → preview → export), but the internal architecture uses a pipeline/operation model that can later be extended to node-based graphs, batch processing, and plugin systems without rewrite.
- **Client-side first.** All processing happens in the browser via Canvas API and Web Workers. No server calls, no uploads. This preserves privacy, eliminates latency, and simplifies deployment.
- **Containerized development.** The entire dev and build environment is wrapped in Docker + Compose. A single `docker compose up` starts the dev server with hot reload. No host-level Node.js or npm required.
- **Engine-agnostic output.** Exports follow widely-adopted conventions (Aseprite-compatible JSON, standard PNG) that any game engine can consume. No engine-specific metadata is generated.

---

## 2. User Personas

**Primary:** Solo indie developer or hobbyist working with 2D pixel art who has a folder of individual frame PNGs (e.g., generated by AI tools, hand-drawn, or extracted from reference sheets) and needs to assemble them into a properly structured sprite sheet with metadata.

**Secondary:** Developer who needs quick image operations on game assets — scaling with nearest-neighbor interpolation, palette reduction, background removal — without opening a full image editor.

## 3. Feature Specification

### Phase 1 — Sprite Sheet Assembly (MVP)

This is the core deliverable. All other features depend on this foundation.

#### 3.1 Image Import

- Drag-and-drop or file picker for multiple PNG files.
- Images appear as thumbnails in an import panel.
- No assumed ordering — files arrive unordered regardless of filename.
- Display filename, dimensions, and file size per thumbnail.
- Warn on dimension mismatches (e.g., mixed 32×32 and 64×64 frames) but do not block — users may intentionally mix sizes.

#### 3.2 Frame Arrangement

- Drag-and-drop reordering of frames in a visual list/grid.
- Configurable grid layout:
  - Number of columns (rows auto-calculated from frame count, or vice versa).
  - Number of rows (columns auto-calculated).
  - Or explicit rows × columns with overflow handling.
- Padding controls:
  - Border padding (outer edge of sheet).
  - Cell padding (spacing between frames).
  - Inner padding (transparent margin within each frame cell — useful for engines that sample neighboring pixels).
- Option to extrude edge pixels by N pixels (prevents texture bleeding in engines with bilinear filtering).
- Live preview of the assembled sheet, zoomable and pannable.

#### 3.3 Animation Tagging

- Select a range of frames and assign a tag name (e.g., "idle", "walk", "attack").
- Each tag stores: name, start frame index, end frame index, direction (forward / reverse / ping-pong), and frame rate in FPS.
- Default frame rate: 10 FPS, overridable per-tag. Duration per frame is derived as `1000 / fps` ms (e.g., 7 FPS → ~143ms per frame).
- Per-frame duration customization is a Phase 2 enhancement. Phase 1 uses uniform timing within each tag.
- Tags are purely metadata — they define named sequences within the flat frame list.

#### 3.4 Animation Preview

- Inline playback of the assembled sprite sheet or of a selected tag.
- Play/pause, frame-by-frame step, speed control (0.25×–4×).
- Onion-skinning toggle: overlay previous/next N frames at reduced opacity.
- Current frame indicator in the frame list and on the sheet preview.

#### 3.5 Duplicate Frame Detection and Cleanup

Duplicate detection is a **UI-first feature**, not just metadata. The primary goal is to let the user visually identify redundant frames across animations and remove them before export, reducing atlas size.

**Visual grouping:**

- On import (or on-demand), compute a perceptual hash for each frame.
- Frames that belong to the same duplicate group receive a shared colored border in the frame list, the sheet preview, and the animation timeline.
- Each duplicate group gets a distinct color (auto-assigned from a palette of high-contrast colors). For example: group A = cyan border, group B = magenta border, group C = orange, etc.
- If a frame is unique (no duplicates), it has no special border.
- Hovering a duplicate-marked frame highlights all other members of its group (e.g., pulse or brighten their borders) so the relationship is immediately visible even when frames are far apart in the list.

**Cleanup workflow:**

- Clicking a duplicate group badge (or right-click → "Show duplicates") filters/scrolls the frame list to show all members of that group side by side.
- The user can then select which frame(s) to keep and which to remove. Removing a frame updates the grid layout and tag indices automatically.
- A summary bar shows: "N duplicate groups found, M frames removable" with a quick action to auto-remove all duplicates (keeping the first occurrence in frame order per group), subject to confirmation.

**Concrete example:** Idle animation (frames 0–3) and walk animation (frames 4–11) share the same default stance as frame 0 and frame 4. Arty detects these are identical, marks both with a cyan border. The user removes frame 4, the walk tag adjusts to start at the new index, and the sheet loses one column.

**Configuration:**

- Threshold sensitivity: exact pixel match (default) or perceptual near-match with configurable tolerance.
- Option to include/exclude alpha channel in comparison (relevant when background removal has been applied).

#### 3.6 Metadata Export (Aseprite-Compatible JSON)

The exported JSON follows the Aseprite json-array format, which is the de facto standard consumed by most game engines and frameworks. Structure:

```json
{
  "frames": [
    {
      "filename": "sprite_00.png",
      "frame": { "x": 0, "y": 0, "w": 32, "h": 32 },
      "rotated": false,
      "trimmed": false,
      "spriteSourceSize": { "x": 0, "y": 0, "w": 32, "h": 32 },
      "sourceSize": { "w": 32, "h": 32 },
      "duration": 100
    }
  ],
  "meta": {
    "app": "Arty",
    "version": "1.0.0",
    "image": "spritesheet.png",
    "format": "RGBA8888",
    "size": { "w": 256, "h": 128 },
    "scale": "1",
    "frameTags": [
      {
        "name": "idle",
        "from": 0,
        "to": 3,
        "direction": "forward",
        "color": "#00000000"
      }
    ],
    "duplicates": [
      {
        "hash": "a1b2c3d4",
        "frameIndices": [2, 7]
      }
    ]
  }
}
```

Key decisions:

- `frames` uses the array format (not hash-keyed) for simpler programmatic access.
- `frameTags` follow Aseprite's convention: `name`, `from`, `to`, `direction`.
- `duplicates` is an Arty extension (not in Aseprite's format) listing perceptual hash groups for LLM or tooling consumption. Engines that don't recognize it simply ignore it.
- `rotated` and `trimmed` are always `false` in Phase 1 (no trim/rotation packing). Included for format compatibility.

#### 3.7 Export

- Export as PNG (sprite sheet image) + JSON (metadata), packaged as a ZIP or as individual file downloads.
- Configurable output filename base (default: input folder name or "spritesheet").
- PNG export settings: bit depth (8-bit RGBA default), optional indexed color mode.

### Phase 2 — Image Operations

These operations work on individual images or on the assembled sheet. Each is an entry in the operation stack.

#### 3.8 Scaling

- Integer scale factors for pixel art: 1×, 2×, 3×, 4×, etc.
- Interpolation modes: Nearest-neighbor (default for pixel art), bilinear, bicubic.
- Scale up or down. Warn when downscaling non-integer factors on pixel art (lossy).

#### 3.9 Palette Operations

- **Reduce to N colors:** Median-cut or k-means quantization with configurable color count.
- **Map to palette:** Import a palette file (`.gpl` GIMP, `.pal` RIFF, `.hex` Lospec, `.ase` Aseprite, or JSON array of hex values) and remap all pixels to nearest palette color. Export palette in any of these formats, selectable during export. Support for well-known palettes (PICO-8, NES, Game Boy, etc.) as built-in presets.
- **Dithering options:** None, Floyd-Steinberg, ordered (Bayer matrix), with strength control.
- **Extract palette:** Generate a palette from the current image(s) for reuse.

#### 3.10 Background Removal

- **Color-key removal:** Click a pixel (or enter a hex value) to set the transparency key color. All pixels matching that color (within a configurable tolerance) become transparent.
- **Contiguous mode:** Only remove connected regions of the key color (flood-fill based), leaving interior pixels of the same color intact.
- **Edge refinement:** Optional 1px anti-alias cleanup along the boundary between removed and retained regions.

---

### Phase 3 — Advanced Features

#### 3.11 Sprite Sheet Slicing (Reverse Operation)

- Import an existing sprite sheet and define a grid (cell width × height) to slice it into individual frames.
- Auto-detect grid from visual gaps or consistent spacing.
- Sliced frames feed into the same pipeline as individually imported images.

#### 3.12 Batch Processing

- Define an operation pipeline (e.g., scale 2× → reduce to 16 colors → export).
- Apply it to a set of input files.
- Output follows a naming convention: `{original_name}_processed.png`.

#### 3.13 Trim and Pack

- Trim transparent borders from each frame, tracking the offset in `spriteSourceSize`.
- Bin-packing layout (as alternative to grid) for irregular-size frames, minimizing atlas waste.
- Set `trimmed: true` and populate `spriteSourceSize` accordingly in the JSON export.

#### 3.14 Operation Presets

- Save a configured operation stack as a named preset.
- Load presets for quick reuse across projects.
- Presets stored in localStorage (or IndexedDB), exportable as JSON.

## 4. Architecture

### 4.1 Tech Stack

| Layer | Technology | Rationale |
|---|---|---|
| UI framework | SvelteKit (SPA mode) | Reactive, minimal overhead, good DX for complex interactive UIs. SPA mode (adapter-static) for client-only deployment. |
| Language | TypeScript (strict mode) | Type safety across the operation pipeline, canvas interactions, and state management. |
| Image processing | Canvas API + OffscreenCanvas in Web Workers | Keeps the UI thread responsive during heavy operations (quantization, hash computation, large sheet assembly). |
| State management | Svelte stores (writable/derived) | Native to Svelte, sufficient for the operation stack model. No external state library needed. |
| Persistence | IndexedDB (via idb wrapper) | Auto-save project state and source image blobs. Survives page reload. Manual `.arty.json` export/import for portability. |
| Containerization | Docker + Docker Compose | Wraps the entire dev environment and build toolchain. Single `docker compose up` for development. Eliminates host-level Node.js/npm dependency management. Compose services: `app` (SvelteKit dev server / production static build). |
| Build | Vite (via SvelteKit) | Fast HMR, good TypeScript support, tree-shaking. |
| Testing | Vitest + Playwright | Unit tests for processing logic, E2E tests for UI workflows. |

### 4.2 Core Data Model

```typescript
/** A single imported image, immutable after creation */
interface SourceFrame {
  id: string;                  // UUID
  filename: string;
  originalBlob: Blob;          // Original file, never modified
  width: number;
  height: number;
  perceptualHash?: string;     // Computed on import or on-demand
}

/** A named animation sequence within the frame list */
interface AnimationTag {
  name: string;
  from: number;                // Start index (inclusive)
  to: number;                  // End index (inclusive)
  direction: 'forward' | 'reverse' | 'pingpong';
  fps: number;                 // Frames per second (uniform within tag)
}

/** Grid layout configuration */
interface GridConfig {
  columns: number;
  rows: number | 'auto';       // 'auto' = ceil(frameCount / columns)
  borderPadding: number;       // px
  cellPadding: number;         // px
  innerPadding: number;        // px
  extrudeEdges: number;        // px, 0 = disabled
}

/** A single operation in the non-destructive stack */
interface Operation {
  id: string;
  type: OperationType;
  enabled: boolean;
  params: Record<string, unknown>;
  order: number;
}

type OperationType =
  | 'scale'
  | 'palette-reduce'
  | 'palette-map'
  | 'background-remove'
  | 'trim'
  | 'dither';

/** Top-level project state */
interface ArtyProject {
  frames: SourceFrame[];       // Ordered by user arrangement
  frameOrder: string[];        // Frame IDs in display/export order
  tags: AnimationTag[];
  grid: GridConfig;
  operations: Operation[];     // Ordered stack, applied sequentially
}
```

### 4.3 Processing Pipeline

```
Source Frames (immutable Blobs)
        │
        ▼
┌─────────────────┐
│  Operation Stack │ ← Non-destructive, each op reads from previous output
│  (Web Worker)    │
│                  │
│  1. scale        │
│  2. palette-map  │
│  3. bg-remove    │
│  ...             │
└────────┬────────┘
         │
         ▼
  Processed Frames (ImageBitmap[])
         │
         ▼
┌──────────────────┐
│  Grid Assembler   │ ← Arranges into sheet per GridConfig
│  (Web Worker)     │
└────────┬─────────┘
         │
         ▼
  Final Sheet (Canvas → PNG Blob)
  + JSON Metadata
```

Each operation receives an `ImageBitmap` and returns a new `ImageBitmap`. Operations are pure functions — no side effects, no shared mutable state. This makes the pipeline trivially parallelizable per-frame and easy to cache (if an operation's params haven't changed, reuse previous output).

### 4.5 Extension Points

The architecture is designed so that future capabilities slot in without restructuring:

- **New operation types:** Add a new file in `operations/`, implement the `Operation` interface, register in the operation type registry. The pipeline, stack UI, and serialization handle it automatically.
- **Node-based editor:** The pipeline is already a DAG of operations with typed inputs/outputs. A node UI would be a different view over the same underlying model, replacing the linear stack rendering but not the execution engine.
- **Batch mode:** The pipeline is already per-frame. Batch processing means looping the same pipeline over multiple input sets and collecting outputs — a thin wrapper around the existing `pipeline.ts`.
- **3D assets:** A future concern, but the project/operation model is format-agnostic. 3D operations would be new operation types with different input/output types (meshes instead of bitmaps).
- **Plugin system:** Operations are isolated pure functions. A plugin API would expose the operation interface and registration mechanism, allowing third-party operations to be loaded at runtime.

```

│            │                          │              │
├────────────┴──────────────────────────┴──────────────┤
│  Animation Timeline / Player                         │
```

- **Frame List** (left): Vertical strip of thumbnails. Drag handles for reordering. Multi-select for tag assignment or batch deletion. - **Animation Timeline** (bottom): Horizontal frame strip for the selected tag. Playback controls, speed slider, onion-skin toggle. FPS control per tag.

## 6. Implementation Phases

### Phase 1 — MVP (Sprite Sheet Assembly)

Scope: Features 3.1–3.7. The minimum useful tool.

Milestones:

1. **Project scaffold:** Docker + Compose setup, SvelteKit SPA, TypeScript strict, Vite config, base layout shell.
2. **Persistence layer:** IndexedDB schema (projects, frames, presets), auto-save on state change (debounced), project list/switcher UI, `.arty.json` export/import.
3. **Import + frame list:** File drop zone, thumbnail rendering, drag-and-drop reorder.
4. **Grid assembly + preview:** GridConfig controls, canvas-based sheet assembly with live preview.
5. **Animation tagging + player:** Tag CRUD with FPS control, timeline component, playback engine.
6. **Duplicate detection:** Perceptual hash computation in Web Worker, color-coded group borders, cleanup workflow UI.
7. **Export:** PNG rendering from canvas, Aseprite-compatible JSON generation, ZIP download.
8. **Polish:** Keyboard shortcuts, undo/redo (command pattern over project state), responsive layout.

### Phase 2 — Image Operations

Scope: Features 3.8–3.10.

Milestones:

1. **Operation stack infrastructure:** Stack UI component, operation registry, pipeline executor in Web Worker.
2. **Scale operation:** Integer scaling with nearest-neighbor. Preview integration.
3. **Palette operations:** Quantization algorithms, palette import/presets, dithering.
4. **Background removal:** Color-key picker, tolerance control, contiguous mode.

### Phase 3 — Advanced Features

Scope: Features 3.11–3.14. Prioritized by user demand.

## 7. Technical Constraints and Decisions

- **Maximum sheet size:** Capped at 4096×4096px by default (configurable up to 8192×8192). Most GPUs and game engines have texture size limits. Warn when the assembled sheet exceeds common limits.
- **Memory management:** Large sheets with many frames can consume significant memory. Use `ImageBitmap` (transferable, GPU-backed) over `ImageData` where possible. Release intermediate bitmaps after pipeline stages complete.
- **Web Worker communication:** Use `postMessage` with transferable objects (`ImageBitmap`, `OffscreenCanvas`). Avoid serializing large pixel arrays as JSON.
- **Undo/redo:** Implemented as a command stack over the `ArtyProject` state. Each user action (reorder, add tag, change grid config, toggle operation) produces an undoable command. The preview is a derived view — undo reverts the project state and the preview recomputes.
- **File size limits:** Warn on individual files >10MB or total import >100MB. These aren't hard limits but performance guardrails.
- **Browser support:** Targets modern evergreen browsers (Chrome, Firefox, Safari, Edge). Requires `OffscreenCanvas` and Web Worker support. No IE11.

---

## 8. Out of Scope (Explicit Non-Goals for v1)

- **Pixel art drawing/editing.** Arty is a processing and assembly tool, not an editor. Use Aseprite, Pixelorama, or similar for creating art.
- **Real-time collaboration.** Single-user tool.
- **Cloud storage or accounts.** All data stays local.
- **3D asset processing.** Architecture accommodates it; implementation is deferred.
- **GIF/APNG/WebP export.** PNG-only for Phase 1. Animated format export is a Phase 3 candidate.
- **Node-based pipeline editor.** The architecture supports it; the UI is deferred.

## 9. Success Criteria

The MVP is complete when a user can:

1. Run `docker compose up` and access Arty in the browser.
2. Drop a folder of unordered PNG frames into Arty.
3. Reorder them via drag-and-drop.
4. Configure a grid (e.g., 8 columns, auto rows, 1px cell padding).
5. Define animation tags with FPS (e.g., "idle" = frames 0–3 at 10 FPS, "run" = frames 4–11 at 12 FPS).
6. Preview the animation playing back correctly.
7. See duplicate frames visually marked with color-coded borders, identify cross-animation redundancies, and remove them to reduce sheet size.
8. Export a sprite sheet PNG + Aseprite-compatible JSON that loads correctly in Godot, Unity, Phaser, or any framework with Aseprite JSON support.
9. Close the browser, reopen Arty, and find the project exactly as it was left (auto-persisted).

## 10. Resolved Decisions

- **Project persistence:** IndexedDB-backed auto-save from Phase 1. Projects are saved automatically on every meaningful state change (debounced). A project list view allows switching between projects. Manual "Export Project" / "Import Project" as `.arty.json` files for portability and backup. Source image blobs are stored in IndexedDB alongside the project state, so reopening a project does not require re-importing files.
- **Palette file formats:** All relevant formats are supported for both import and export, selectable during export: `.gpl` (GIMP Palette), `.pal` (RIFF/Microsoft), `.hex` (Lospec, one hex color per line), `.ase` (Aseprite Palette), and JSON (array of hex strings). Built-in presets (PICO-8, NES, Game Boy, etc.) are bundled as JSON internally.
- **Frame duration granularity:** Uniform duration per tag for Phase 1, specified as FPS (frames per second). The per-frame duration in the export JSON is computed as `1000 / fps` (rounded to integer ms). Example: a 4-frame "idle" tag at 7 FPS → 143ms per frame, ~571ms total. Per-frame duration customization is deferred to Phase 2.
